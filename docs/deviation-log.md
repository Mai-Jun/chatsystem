# 开发偏离记录（Deviation Log）

> 记录开发过程中偏离原计划的决策/事件：原因、处理办法、后续影响。
> 本文件随每次重大偏离追加；环境类坑位细节仍在 `docs/env.md`，流程约定见 `docs/HANDOFF.md`。
> 建立：2026-10-12（M10 部署固化轮次）。

## D1：服务器资源抖动失联（2026-10-12，M10 轮次）

**事件**：M10 轮次开工后约 1 小时（21:00 左右），阿里云服务器 SSH 进入"横幅交换超时"状态，
随后网关 `/health` 也开始无响应（ping 通、TCP 22 可建连）。持续约 X 小时自行恢复（待回填）。

**原因**：本轮为赶进度，把两类重型操作排成了并行：
1. 我（协调会话）在后台启动了 ES 镜像拉取（`docker pull elasticsearch:7.17.23`，约 600MB 解包写盘）；
2. 同时 WS1 工作流在服务器上重建 `message_storage_server`（编译 brpc 相关 TU，单 cc1plus 内存峰值可用 500MB~1GB）；
3. 叠加常驻负载（MySQL/RabbitMQ/etcd/Redis + 7 个应用服务，used≈735MB）。

服务器仅 2核1.6G，IO 与内存双重挤压下系统进入重度 swap 抖动（与文档坑 1 记录的
"-j2 编译后 sshd 失联约 2.5 小时"同源，此次触发因素是「镜像解包 + 编译」并发）。

**影响**：
- WS1 的服务端二进制重建中断（服务未重启，运行中实例仍是旧二进制；旧 SELECT 不含 seq 列，
  与已应用的 seq 迁移列兼容，期间功能无损）；
- 两个工作流的联网验收（dual_client_push×3 / client_smoke / GUI 复验）全部暂停；
- 本地开发（代码修改、Windows 构建、文档）不受影响，按计划推进。

**处理办法**：
1. 立即停止一切对服务器的 SSH 重试（避免新连接加重卡滞），改为单来源低频探针
   （每 60s 一次 `/health`，恢复即通知）；
2. 向两个在跑工作流下发"停止 SSH、转本地收尾"指令；
3. 恢复后按「**重型操作严格串行**」重排所有服务器任务：先重建单服务 → 重启 → 该项验收 →
   再做下一件重型操作（镜像构建/ES 启动/容器切换），每步之间确认系统负载回落。

**教训固化**（写入 HANDOFF 坑位速查）：
- 2核1.6G 服务器上，「编译」「镜像拉取/解包」「容器构建」三者**任何时候只允许一件事在进行**；
- 重型操作前先停不必要的容器/服务释放内存（沿用 M4 事故对策），完成后立即回归常规负载；
- 远程批量操作前先看 `free -m` 与 `uptime` 负载值。

**状态**：已收尾——用户于 23:34 重启服务器恢复；恢复后按串行纪律补完了 seq 修复重建与全部验收
（dual_client_push×3 全过 + smoke + e2e，详见自检报告）。

**D1-后续事件（22:50 用户重启前的二次抖动）**：重启前服务器始终未自行恢复（约 2 小时），
用户手动重启。重启后教训落地检查：重建 message_storage_server 单操作、成功（90 秒内完成）。

## D5：ES 容器 512m 堆 + 全栈叠加二次触发抖动（2026-10-12 深夜）

**事件**：服务器重启恢复、7 服务全部拉起并通过 seq 验收后（约 23:55~00:05），我执行
`docker start im-es`（**dev compose 创建的旧容器，堆仍是 512m**）→ ES 启动约 1 分钟后
SSH 再次进入横幅超时。

**原因分析**：
1. 新的 ES 容器还未按 256m 重建——我改动的是 `docker-compose.prod.yml` 与 dev compose 文件，
   但正在运行的容器是**变更前创建**的（环境变量在建容器时固化），`docker start` 沿用 512m 堆；
2. 实测数据：ES(512m) 起来后 `used 1283M / available 135M`——1.6G 机器已无余量，
   ES 启动期自身的 JVM 预热 + Lucene 段加载把系统推入 swap 抖动；
3. 我随后又执行了一次 `docker start im-es` 重试（判断失误：当时误以为 9200 公网不通=ES 未起，
   实际那是安全组未放行 9200 的正常现象，ES 当时是畅通的）——二次启动放大了压力。

**处理办法**：
1. 停止一切重试，等服务器自行恢复；
2. 恢复后第一件事：**停掉 ES 容器**（防反复抖动），其余服务保持运行；
3. ES 改用 **256m 堆重建容器**（`docker compose ... up -d --force-recreate elasticsearch`），
   且启动严格控制为「一切稳定后的最后一步」；观察 5~10 分钟内存与 SSH 可响应性后再做索引/搜索验收；
4. 若 256m 仍不稳定 → 按 PLAN 的 **prod-minimal 档位**交付（ES 不启用、搜索走 LIKE 降级），
   并把「ES 上机需 4G+ 升配」记入 M10 结论——这正是 PLAN 预留的"实测后定档位"决策点。

**教训补充**（并入 D1 的纪律）：
- **改配置 ≠ 生效**：compose 的 `environment` 改动只对**新建容器**生效，必须显式
  `--force-recreate` 重建；对"Exited"状态的旧容器直接 `docker start` 会沿用旧配置（本次即此陷阱）；
- **观察面要对立正确**：服务器 9200 未对公网放行，ES 健康只能从服务器内部（SSH 内 curl）验证，
  不能用「本地 curl 9200 不通」推断 ES 故障；
- 重启恢复后、做任何验证前，先检查关键容器的**实际生效配置**（`docker inspect` 看 Env）。

**状态**：待服务器恢复后执行上述计划（先停 ES → 切 prod 栈跑核心回归 → 最后单独试 ES 256m）。

## D6：ES 查询 JSON 括号 bug——潜伏自 M6，首次上机才暴露（2026-10-13）

**事件**：ES 256m 成功上机、索引建立、231 条存量回填后，搜索请求均返回 400，
自动降级 MySQL LIKE（`search` 日志 `ES 搜索失败: status=400` → `搜索降级 MySQL LIKE`）。

**根因**：`message_storage_server/main.cc` 拼装的查询 JSON 多一个 `]`——
`"...asr_text\"]}}]"` 中 `]` 提前关闭了 `must` 数组，使后续（可选的 term 或收尾的 `]}}`）成为
语法错误。**该 bug 自 M6 写出就存在，但 M6~M9 期间 ES 从未部署**（一直走 LIKE 降级路径），
代码从未被执行——降级设计在保证可用性的同时，也长期掩盖了这个 bug。

**修复**：删掉多余的 `]`（只关闭 multi_match 两层对象，must 数组与 term 共用最后的 `]}}`），
重建消息存储服务并复验走 ES 路径。

**教训固化**：
- 「降级路径」的测试价值：有降级设计的组件必须**分别验证主路径与降级路径**，
  否则主路径的 bug 会被降级掩盖到生产才暴露；
- 新增/修复后先单独 curl 复现验证，再上服务验证（本次正是靠 curl 手写查询成功、
  服务端查询失败，定位到"拼装与手写不一致"）。

**状态**：修复代码已上传并将随 message_storage_server 重建生效（服务器恢复后复验）。

## D7：第三次资源抖动——违背自定纪律（2026-10-13 凌晨）

**事件**：D6 修复上传后，在 **ES（256m）已在运行**的情况下直接编译 message_storage_server，
SSH 再次进入横幅超时（约 01:15）。

**自我复盘**：D1/D5 已固化「编译 / 镜像 / ES 启动 只允许一件事在进行」，
本次失误在于把「ES 已稳定运行」当成了例外（ES 静置占用约 530MB RSS + JVM 后台负载，
编译峰值叠加后仍然越线）。**纪律修正：编译前一律 `docker stop im-es`（内存即释放），
编译与重启完成后再起回**——不再区分"ES 是否稳定"。

**处理**：等待服务器自行恢复（内存漂移类抖动通常较快恢复），恢复后按
「停 ES → 重建 → 重启 → 起 ES → ES 搜索复验」串行执行。

**D7-状态更新（2026-10-13 04:25）**：**本次未自行恢复**——失联持续 3 小时+（02:00~04:25 多次
探测：ping 通 15ms、22 不通、9000/9001 TCP 可建连但应用层无响应），超出前两次（D1/D5）的
2~2.5 小时恢复窗口。判定需要再次人工重启服务器（与 D1 处置相同）。恢复后剩余收尾项：
1. `docker start im-es` 之前先确认各容器状态（重启后全部 Exited，先 `docker compose -f
   docker/docker-compose.prod.yml up -d` 拉起全栈）；
2. **停 ES**（`docker stop im-es`）→ 重建 `message_storage_server`（systemd-run -j1）→
   `docker restart im-message-storage-server` → 起 ES；
3. ES 搜索主路径复验（日志出现 `ok(es)`）+ 停 ES 降级复验；
4. ~~服务器侧 `git fetch` → `git push origin main` 代推 GitHub~~ ✅ **已由本地直推完成**
   （04:38 网络窗口期直连 GitHub 成功，`de87318..76e9844` 全部上仓——推送不再依赖服务器，
   服务器恢复后仅需普通 `git fetch origin main` 追平）；
5. 公网 Windows 双端验证 + checklist/自检报告终稿。

**纪律根本修正**（本轮三次事故的最终结论）：这台 2核1.6G 服务器上的**任何编译动作前，必须先
`docker stop im-es`**（无论 ES 当前是否"稳定运行"）；大规模容器操作（镜像构建/切换）与编译
互斥。后续若频繁迭代，建议临时升配到 4G 或把编译迁到本地交叉/CI（PLAN 已有 prod-full 档位评估）。

**D7-第四次复发（2026-10-13 10:35）**：修复 D6 后我在 ES 运行状态下编译 e2e 测试——再次触发
横幅超时。**这是同一纪律一天内第二次被我自己违反**，说明"靠记性遵守"不可靠。工程化修正：
新增 `scripts/safe_build.sh` 包装脚本（**停 ES → -j1 + MemoryMax 编译 → 起 ES 并等 green**），
此后所有服务器编译一律走 `bash scripts/safe_build.sh [target]`，从机制上消除再犯可能。
教训：**纪律应固化为工具，而不是依赖人的注意力**。

## D8：停机操作也要串行——资源约束教训的第五副面孔（2026-10-13 傍晚）

**事件**：项目交付后按用户要求停服释放资源，执行 `docker compose -f ... stop`（**并行**停
全部 12 个容器）→ 服务器再次进入 SSH 横幅超时，整机停机操作卡死；用户重启后用**串行停机
脚本**（逐个 `docker stop -t`：应用服务 7 个 → ES 45s → MQ/Redis/etcd → MySQL 45s，每步
间隔 2s）顺利完成——0 容器运行、内存从 1.2G 降至 299M、全程 SSH 可用。

**根因归纳（五副面孔同一根因）**：这台 2核1.6G 服务器上，**任何"多个内存/IO 大户同时动作"
的操作都会触发 swap 抖动**。已发现的面孔：
1. 编译并行（-j2）→ OOM 失联（D1 前身）；
2. 镜像解包 + 编译并发 → 失联（D1）；
3. ES(512m) 启动 + 全栈 → 失联（D5）；
4. ES 运行时编译 → 失联（D7）；
5. **compose 并行停全部容器（ES+MySQL 同时关机刷盘）→ 失联（D8，本文）**。

**处置固化**：
- 停机脚本改为串行分阶段（本次已用；形如 `for c in ...; do docker stop -t N "$c"; sleep 2; done`）；
- 启停规约并入 README 级文档（HANDOFF 第六节操作手册）：**启/停/编译/镜像操作一律串行**，
  拒绝任何形式的"并行批处理"。
- 对 4G+ 机型此约束放宽（PLAN 档位预案）。

**状态**：已执行完成（服务器当前 0 服务运行、资源已释放、数据完好）。

## D3：sync_latest 分页游标错误（代码复查发现，2026-10-12）

**偏离**：WS4 首版 `sync_latest_page()` 递归翻更旧页时用了本页**最新**一条的时间戳做游标，
会导致空档 >1 页时重复拉取同一页直至 20 页上限。

**处置**：协调者复查 diff 时发现（服务端返回升序、页首=最旧，游标应取 `messages(0)`），
反馈 WS4 修正并重编译 + GUI 冒烟复验通过。**教训**：分页游标方向必须与接口返回排序语义核对，
不能凭"翻页=向更旧"的直觉；此类 bug 静态审查可捕获，说明"改动后协调者复核 diff"环节有价值。

**D3 补充（协调者加固，同日）**：复查又发现插入时序问题——补拉是多轮异步查询，期间实时推送
可能先落到列表末尾（重连场景推送先恢复、翻页响应后到），原实现把补拉历史统一"追加到末尾"
会插在更新的消息之后（显示错序）。已改为**从尾部回扫定位插入点**（跳过 create_time 更新的
消息，正常无并发时即表尾，行为不变），重编译 + GUI 冒烟通过。同秒边界仍依赖到达顺序，
属已知限度（proto 游标只有秒级时间戳，见 WS4 汇报遗留项）。
