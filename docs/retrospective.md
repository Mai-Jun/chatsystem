## 一、一句话总览

一个**从零开始、纯服务器环境开发**的分布式 IM 系统：C++17 写 7 个微服务 + Qt6 桌面客户端，
部署运行在 2核1.6G 公网云服务器上，支持四类消息（文本/图片/文件/语音）、好友/群聊、
实时推送、离线补历史、中文分词搜索、Docker 容器化自愈部署——**全功能端到端可运行、可验收、
可演示**。

开发历时（有效提交日）：**10-05 规划 → 10-06 骨架~M6 → 10-07 M7~M9 三轮 UI 迭代 → 10-08 换机 →
10-12~13 M10 部署固化 + 微信风格 UI 大改版**。约 3 个高强度工作日 + 1 天收尾，
共 80+ 次提交。

## 二、开发模式（理解项目的第一把钥匙）

这个项目能从零到全功能只用了几天，靠的是四个固定的工作模式。**理解这四个模式，
后面所有过程细节都能对号入座**。

### 模式 1：服务器即开发环境（云端开发）
- 开发机是 Windows（只有编辑器 + git），**代码编译、运行、测试全在阿里云服务器**（Ubuntu 22.04）上；
- 原因：最初本地 WSL2 不可用（旧机系统组件损伤），改为直接用云服务器；
  Windows 端只保留 MSYS2 用于编译 Qt 客户端（因为要交付本机可双击的 exe）；
- 结果：后端与运行环境零差异（同机编译同机跑），没有"本地好好的服务器挂了"这类问题。

### 模式 2：文档驱动 + 里程碑驱动
- 一切按 `docs/PLAN.md` 的 **M0~M10 里程碑表**推进：每阶段有明确验收标准，
  完成后在 PLAN 上打勾并写验收证据；
- **跨会话续接靠 `docs/HANDOFF.md`**（每次阶段结束更新）：新会话/新机器读它就能30秒恢复上下文——
  这个项目实际经历了多次会话中断（上下文用尽、换机器），全靠这套文档无损续接；
- 每个决定记入文档（决策记录），每个坑记入 `docs/env.md`（坑位速查）。

### 模式 3：完成 = 可运行 + 可验收（验证先行）
- 每个里程碑**不是"代码写完"就完成，而是"验收工具跑通"才完成**；
- 验收体系分四层（详见第五节）：单元测试 → 协议冒烟 → 端到端脚本 → GUI 截图验证；
- 每个里程碑都有专属验收工具，且**这些工具被保留下来反复复跑**（回归测试），
  不是一次性脚本。

### 模式 4：小步提交 + 事故即文档
- 80+ 次提交基本是"一个功能/一个修复一次提交"，提交信息写清为什么；
- 每次事故（编译 OOM、服务挂掉、服务器失联）处理完立即写进文档——
  最后形成了 7 条完整的事故记录（deviation-log D1~D7）+ 24 条踩坑速查。

## 四、真实 bug 与事故全景（这个项目最有价值的部分）

### 4.1 四个"真 bug"（都是隐蔽型，值得反复讲）

| # | Bug | 潜伏期 | 怎么发现的 | 根因 |
|---|---|---|---|---|
| 1 | **网关 MQ 桥接永不重试** | 从 M7 就存在 | 容器化后推送全挂但 HTTP 全正常 | `MqSubscriber::start()` 连接失败即放弃，消费循环（含重连逻辑）根本没启动；容器编排下网关可能先于 RabbitMQ 就绪 |
| 2 | **MQ 空闲超时误判** | 从 M7 就存在 | 修 #1 后日志出现 3 秒一次的重连噪音 | `amqp_simple_wait_frame_noblock` 返回 `AMQP_STATUS_TIMEOUT`（空闲）被当作连接故障 |
| 3 | **ES 查询 JSON 多一个括号** | **从 M6 就存在** | ES 首次上机后搜索全部 400 | 查询拼装 `"...}}]"` 提前关闭 must 数组；**M6~M9 期间 ES 从未部署，这行代码从未被执行过**——降级设计（LIKE）长期掩盖了主路径 bug |
| 4 | **消息同秒排序不稳** | 从 M6 就存在 | 专项测试连发 12 条复现乱序 | create_time 是秒级精度，同秒内多条消息 `ORDER BY create_time` 无次序键 |

**共同规律**：4 个 bug 全部是"特定条件才暴露"——容器启动顺序、ES 首次上机、
高并发连发。**正常手工测试永远测不出来**。信任来源：①自动化测试造极端条件（连发12条）；
②部署形态变化即回归（容器化暴露 #1）；③"从未执行的代码路径 = 未知风险"的敏感（ES 上机暴露 #3）。

### 4.2 服务器资源事故（4 次，同一个根因）

2核1.6G 的服务器上，「编译」「ES 运行」「镜像解包」都是内存大户，**并发即失联**：

| 次 | 触发组合 | 后果 | 处理 |
|---|---|---|---|
| D1 | ES 镜像解包 + 服务端编译 | 失联 2h+ | 用户重启；纪律：重型操作串行 |
| D5 | ES 容器(512m)启动 + 全栈 | 失联 | 用户重启；ES 降 256m（实测稳定） |
| D7 | ES 运行时编译存储服务 | 失联 | 用户重启；纪律：编译前必停 ES |
| D7-复发 | ES 运行时编译 e2e 测试 | 失联 | **工具化：写 `safe_build.sh` 把纪律变成代码** |

**这段过程的价值**：它真实演示了"**纪律靠不住，工具才靠得住**"——同一个错误我犯了两遍，
第三遍改成了包装脚本（自动停 ES → 编译 → 起 ES），从此不再可能犯。
（面试讲"你遇到的最大困难"时这是很好的素材：从事故到流程到工具化的完整闭环。）

3. **CI**：把 4 层验证搬进 GitHub Actions（不过服务器编译过重，建议本地/轻量 runner）。

---

## 八、给"未来的自己"的三条经验

1. **降级设计会掩盖主路径 bug**：有 fallback 的组件，主路径和降级路径**必须分别验证**
   （反向教训：ES 的 LIKE 降级让一个 400 错误潜伏了两天）；
2. **环境变化是最强的测试**：换机、换部署形态（裸进程→容器）各暴露出一批新 bug——
   每次环境变化后必须全量回归；
3. **反复犯的错要工具化**：纪律写在文档里我还会忘，写成 `safe_build.sh` 才真正解决——
   **流程问题用工具解决，不用意志力解决**。
